## B. SEGV の根本原因と回避策

### 3. block-VIEM.jl の FFTW threading 制約

`BlockVIEM.__init__` ([src/BlockVIEM.jl:26-29](file:///home/moteki/Julia/block-VIEM.jl/src/BlockVIEM.jl#L26)) は default で `FFTW.set_num_threads(Threads.nthreads())` を呼ぶ。

**SEGV 発生の閾値** (m2 観測):

| 試行 | L | Julia | FFTW | 総並列度 | 結果 |
|---|:---:|:---:|:---:|:---:|---|
| 過去 production sweep | 100 | 8 | 8 | 6,400 | OK |
| 過去 lc-convergence (m1) | 32 | 8 | 8 | 2,048 | OK |
| **m2 1st 試行** | 128 | 32 | 32 | **131,072** | **SEGV** |
| m2 修正後 | 128 | 32 | 1 | 4,096 | OK |

→ **総並列度 (L × Julia threads × FFTW threads) を ~6,400 程度以下に抑える** のが安全。

**SEGV のスタックトレース特徴**: `libfftw3 spawn_apply` / `FFTW.jl providers.jl:49 spawnloop`。これが出たら spawn-storm 確定。

**重要**: maxiter 短い test (例: maxiter=20) では発生しない。**MAXITER=200 規模の test でしか SEGV 検出できない**ので、本番 config を縮小せず短時間ラン (lc=1.5 単独 = 数分〜十数分) で先に検証する必要あり。

### 4. 修正方法

`run_lc_convergence.jl` 冒頭に `BlockVIEM.set_fft_threads(N)` を入れて override する。m2 では env var `FFT_THREADS` で渡せるよう修正 (commit `5a4ca56`、未 push)。

別案として、過去 paper run と同じ config で走らせれば自動的に安全圏に入る (Julia auto + FFT default で総並列度 << 6,400 になる規模設定)。

## C. 並列性能の本質的な落とし穴

### 5. FFTW plan cache の global lock 競合

`FFTW.set_num_threads(N)` は **process-global の thread pool** を作る。Julia thread が多数 (M 個) 同時に同サイズ FFT plan を呼ぶと、 **cache lock で実質直列化** する模様。

m2 観察: `-t 32 + FFT_THREADS=1` で **大半の時間 1 core のみ動作**、たまに BLAS gemm phase で 16 cores at 50%。 `Threads.@threads for j in 1:L` ([aim_operator.jl:789](file:///home/moteki/Julia/block-VIEM.jl/src/aim_operator.jl#L789)) の意図に反して並列化が効いていない。

これは BlockVIEM の docstring ([aim_operator.jl:769-774](file:///home/moteki/Julia/block-VIEM.jl/src/aim_operator.jl#L769)) では未言及の制約。

**本質解決**: per-thread plan instance 化 (block-VIEM.jl 本体改修)。paper run scope 外。

### 6. `-t N + FFT_THREADS=k` の合理的選択

物理コア数 P に対して、簡易最適は `-t 1 + FFT_THREADS=P`:
- Julia thread 1 個 → cache lock 競合なし
- FFT pool に P 個の thread → FFT 中は P cores 飽和
- ただし matvec の sequential 部分と orthog (BLAS gemm) 比率次第で、Julia threads を増やしても損しない局面もある

m2 で試したベンチマーク (lc=1.5):

| Config | Julia | FFTW | 総並列度 | 観察 |
|---|:---:|:---:|:---:|---|
| (a) | 32 | 1 | 4,096 | 1 core 大半 + BLAS bursts、lc=1.5 で 13 min |
| (c) | 8 | 8 | 8,192 | 25% util、(a) と速度同等 |
| (d) | 1 | 16 | 2,048 | 20% util、(a) と速度同等 (lc=1.5) |

**結論**: **lc=1.5 (small mesh) では各 config の差はほとんど出ない**。FFT が iter 全体に占める比率が小さいため。**lc=0.7 (large mesh) で benchmark しないと意味のある差は見えない**。

## D. 運用上の落とし穴

### 7. `run_lc_convergence.jl` は HDF5 を lc 全完了後の一括書き出し

`write_convergence_h5(...)` が for ループ後に 1 回だけ呼ばれる ([line 306](file:///home/moteki/Julia/block-VIEM.jl/viem_results/paper/run_lc_convergence.jl)) ため、**途中 kill = lc=1.5/1.0 が完走していても全部失う**。

m2 では Phase A 1st 試行で 5h かけて lc=1.5 (98 iter 収束) と lc=1.0 (200 iter stall) を完了させたが、threading 最適化のため kill した結果すべて喪失した。

**対策**:
- 長時間 run の前に lc=1.5 単独 (`LC_FACTORS="1.5"`) で完走させて HDF5 出力構造を確認
- または 各 lc 完了直後に temp HDF5 (例: `convergence_gre_Au.lc15.tmp.hdf5` など) を書き出す patch を加える (10-20 行程度)
- 完了後に temp ファイルをマージして本 HDF5 にする

### 8. Julia の stdout は redirect 時に block-buffered

`> /tmp/log 2>&1` でリダイレクトすると **process 終了か明示 `flush(stdout)` まで何も出ない**。

m2 では (d) benchmark の進捗が見えず「ジョブ固まった?」と何度も誤診した。

**必須対処**: 長時間 run は `stdbuf -oL ~/.juliaup/bin/julia ...` でラップ。これで line-buffered になりリアルタイム監視可能。

または runner の `println(...)` 後に `flush(stdout)` を都度呼ぶ (run_lc_convergence.jl の per-lc table 行はすでに flush 付き、header は未 flush)。

### 9. `ps -o pcpu` は lifetime average、瞬間値ではない

起動時の precompile / 初期化を含むので、定常状態より低く出る。

瞬間並列度の確認:
```bash
top -b -n 1 -H -p PID | grep -E "^\s*[0-9]+ moteki" | awk '{ if ($9 > 50) {n++} } END {print "threads >50% CPU:", n}'
```

m2 で `ps` が `%CPU 596` と表示していたが top 瞬間値は >50% で 32 threads → 実際は steady-state で 28+ cores 使用していた、という判断ずれを起こした。

## E. ベンチマーク設計の教訓

### 10. benchmark は dominant な lc 点で

m2 では lc=1.5 (smallest mesh) で threading config を benchmark したが、FFT 比率が小さく差が出ず判断不能だった。

**Phase A の wall time を支配する lc=0.7 で benchmark** すべき。大 mesh ほど FFT が iter 全体の dominant 比率になり、threading 効果が顕在化。

ただし lc=0.7 1 点完走でも 5h 程度かかる可能性があるため、benchmark とはいえ慎重に config 選定が必要 (短時間で済む小 mesh と本物の trade-off)。

妥協案: `LC_FACTORS="0.7"` + `MAXITER=20` (短縮) で benchmark = per-iter wall time 比較に絞る。**ただし MAXITER=200 で SEGV する config を MAXITER=20 では検出できない** ので、SEGV テストは別途必要。

### 11. A/B 比較は条件揃えて wall time で

per-iter time scaling より **lc 1 点完走 wall time** で比較 (orthog 等他 phase 含む)。

m2 では仮説 (期待 speedup 5×) と実測 (1.1×) の乖離が大きかった。仮説に固執せず**実測優先**で判断すべき。

## F. 戦略的判断の教訓

### 12. 「kill して redo」の決断は定量的に

m2 では Phase A 1st 試行 5h 経過時点で kill して redo した:
- 既消費 5h は sunk cost と認識
- redo 期待値の試算: 期待 speedup 70% 信頼で 1.5-2.5× → 期待値 ~2.2h vs 継続 ~3.4h
- 実測: ベンチマーク段階で 1.1× speedup → 期待値計算が楽観的すぎた

**教訓**: 既消費が大きいときは継続、新規 phase で最適化を適用する戦略のほうが堅実。**特に「動いている」run を kill するのは最後の手段**。

### 13. paper deadline 局面では「動く config」を優先

過去 paper run (production sweep, lc-convergence v1 で部分実行) は `FFT default + Julia auto/8` で動いていた = **既知の安全 config**。

大胆な並列最適化は別タスク (paper 投稿後) として切り分け、**新マシンでは過去 production sweep と同じ config で先に走らせ、結果を確保** すべき。
